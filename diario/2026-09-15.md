# Diário — 03/09/2026

## Exercício 2 — Construam o laço

### Objetivo

O objetivo do exercício foi implementar um agente simples usando **function calling**, com duas tools em Python e um laço limitado por `MAX_PASSOS`. Além de fazer o agente executar ferramentas, o experimento busca observar quanto a **descrição de uma tool** influencia a decisão do modelo.

A ideia central foi manter a implementação da ferramenta, seu nome e seus parâmetros iguais e alterar apenas a descrição apresentada ao modelo. Assim, é possível comparar o comportamento do agente em dois cenários: uma descrição informativa e uma descrição propositalmente vaga.

---

## Implementação

O agente foi implementado em `agente.py` e possui menos de 100 linhas.

Foram criadas duas ferramentas:

- `nome_disciplina()`: não recebe parâmetros e retorna o nome da disciplina;
- `consultar_texto(texto)`: recebe uma string e retorna a quantidade de caracteres, incluindo espaços.

As duas funções possuem docstrings e são declaradas também no formato de **function calling** utilizado pela API do Ollama.

O laço funciona da seguinte forma:

1. a pergunta do usuário é enviada ao modelo junto com as tools disponíveis;
2. o modelo decide se precisa chamar alguma ferramenta;
3. caso exista um `tool_call`, o Python executa a função correspondente;
4. o resultado da ferramenta é devolvido ao modelo como uma mensagem do tipo `tool`;
5. o processo se repete até o modelo produzir uma resposta final ou atingir `MAX_PASSOS = 5`.

Para cada execução são registrados:

- número de passos;
- ferramentas esperadas;
- ferramentas efetivamente chamadas;
- se a escolha das ferramentas foi correta;
- resposta final do modelo.

---

## Cenários comparados

Foram usados dois conjuntos de tools, alterando somente a descrição de `consultar_texto`.

### Cenário A — descrição clara

A descrição apresentada ao modelo é:

```text
Conta quantos caracteres existem no texto informado, incluindo espaços.
```

### Cenário B — descrição vaga

A descrição é substituída propositalmente por:

```text
faz uma consulta
```

O nome da função, os parâmetros e a implementação permanecem exatamente os mesmos.

---

## Casos de teste

Em vez de testar apenas uma pergunta, foram preparados cinco casos. Todos são executados uma vez com a descrição clara e novamente com a descrição vaga.

| Teste | Pergunta | Tool(s) esperada(s) | Resultado da função esperado |
|---|---|---|---|
| T1 | Quantos caracteres existem em `agente`? | `consultar_texto` | `6` |
| T2 | Conte os caracteres de `inteligencia artificial`. | `consultar_texto` | `23` |
| T3 | Informe o nome da disciplina. | `nome_disciplina` | nome da disciplina |
| T4 | Informe o nome da disciplina e conte os caracteres de `modelo`. | `nome_disciplina` + `consultar_texto` | nome da disciplina + `6` |
| T5 | Descubra o tamanho de `function calling`. | `consultar_texto` | `16` |

### Motivo de cada teste

**T1 — chamada direta**  
É o caso mais simples e próximo ao enunciado original. Serve como referência para verificar se o modelo associa diretamente a tarefa de contagem à tool `consultar_texto`.

**T2 — variação de entrada**  
Repete a mesma intenção com um texto maior e contendo espaço. O objetivo é verificar se a escolha da ferramenta continua consistente sem depender da palavra utilizada no primeiro teste.

**T3 — caso-controle**  
A pergunta exige `nome_disciplina`, cuja descrição não foi alterada. Esse teste ajuda a verificar se uma possível queda de desempenho está concentrada apenas na tool que teve sua descrição degradada.

**T4 — uso de duas tools**  
Esse caso exige as duas ferramentas. Ele também testa melhor o funcionamento do laço, porque o modelo pode chamar as duas tools na mesma resposta ou realizar chamadas em passos diferentes antes de chegar à resposta final.

**T5 — reformulação da intenção**  
Em vez de usar explicitamente a expressão “quantos caracteres”, a pergunta pede o “tamanho do texto”. O teste verifica se a descrição da ferramenta ajuda o modelo a relacionar uma formulação diferente à mesma função.

---

## Hipótese

A expectativa é que a descrição clara facilite a seleção de `consultar_texto`, principalmente nos testes T1, T2 e T5.

Quando a descrição é substituída por `"faz uma consulta"`, o modelo recebe menos informação semântica sobre a finalidade da função. Isso pode gerar alguns comportamentos:

- deixar de chamar `consultar_texto`;
- selecionar a ferramenta errada;
- precisar de mais passos até chegar à resposta;
- tentar responder diretamente sem utilizar a ferramenta;
- apresentar maior dificuldade no teste T4, em que duas ferramentas são necessárias.

O T3 funciona como controle, pois a descrição de `nome_disciplina` não muda entre os dois cenários.

## Como executar

Com o Ollama instalado e em execução:

```bash
ollama pull qwen3
python agente.py
```

O programa executa os cinco testes primeiro com a descrição clara e depois com a descrição vaga.

A saída de cada teste apresenta uma estrutura semelhante a:

```text
T1 {"passos": 2, "esperadas": ["consultar_texto"], "chamadas": [...], "correta": true, "resposta": "..."}
```

Os valores impressos podem ser copiados diretamente para a tabela de resultados.

## Análise proposta

Depois da execução, a comparação principal deve considerar dois pontos.

Primeiro, **se a ferramenta correta continuou sendo escolhida** depois que sua descrição foi piorada. Uma diferença entre os cenários indica que a descrição fornecida ao modelo tem papel importante no processo de decisão do function calling.

Segundo, deve-se observar o **número de passos do laço**. Mesmo que o modelo eventualmente chegue à ferramenta correta, uma descrição ruim pode tornar o processo menos direto e aumentar a quantidade de interações necessárias.

O teste T3 é especialmente útil nessa análise. Como `nome_disciplina` possui a mesma descrição nos dois cenários, seu comportamento serve como referência para separar uma possível instabilidade geral do modelo de um efeito relacionado especificamente à descrição modificada.

O T4 também permite observar como o modelo organiza uma solicitação que exige mais de uma ferramenta e se a descrição vaga de uma delas interfere na conclusão de uma tarefa composta.

---

## Conclusão

O exercício mostra que uma tool não é definida apenas pelo código que será executado. Para o modelo, o **schema, o nome, a descrição e os parâmetros** fazem parte da interface utilizada para decidir quando uma ferramenta deve ser chamada.

Por isso, uma descrição precisa funciona como parte do mecanismo de roteamento do agente. O experimento com descrições clara e vaga permite medir esse efeito diretamente, mantendo o restante da implementação constante.

Com os cinco casos adicionados, o teste deixa de depender de uma única pergunta e passa a observar também consistência, variação de linguagem, uso de uma ferramenta de controle e uma chamada que exige múltiplas tools.
